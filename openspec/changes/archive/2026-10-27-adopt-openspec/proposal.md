## Why

This module has never used a spec-driven workflow: no Agent OS, no OpenSpec, no written contract besides the README and the variable descriptions. The sibling modules (`vault`, `keycloak`) already plan changes through OpenSpec with pinned engineering-standards stores. Adopting OpenSpec here, for the first time, gives contributors and coding agents one routing file (`AGENTS.md`), the shared standards, and a baseline contract that future changes write their delta specs against.

## What Changes

- First adoption of OpenSpec: `openspec/config.yaml` references the `quality`, `repository` and `terraform` stores pinned to a tag, with scaleway-iam `context`, per-artifact `rules` and `operations` guidance.
- Add `AGENTS.md` (project summary, non-negotiables, standards lookup, workflow, precedence, commands) and `CLAUDE.md` importing it.
- Install the `openspec-*` skills for Claude Code (`.claude/skills/`) and OpenCode (`.opencode/skills/`).
- Tooling: pin `node` and the `openspec` CLI in `mise.toml`, add `spec-validate` and `spec-setup` tasks, add `scripts/openspec-setup.sh`, and validate specs in CI through the `validate:specs` job (`.gitlab/specs.yml`).
- Write the baseline capability specs under `openspec/specs/`, describing the module **as released today**, including its quirks (see the design).
- README "Contributing" points to the spec workflow.
- `CHANGELOG.md` stays generated by git-cliff from commit subjects; nothing changes there.
- No change to any `.tf` file, input, output or resource. Semver: **patch** (tooling and documentation only); it ships with the next tag.
- There is no `tests/` directory yet; this change does not add one. New behaviour adds `tests/main.tftest.hcl`.

## Capabilities

### New Capabilities
- `module-contract`: supported OpenTofu/Terraform and provider versions, no provider or backend blocks, the inputs (names, types, defaults, required vs optional), the 20 outputs and which ones are sensitive.
- `applications-and-api-keys`: IAM applications, API keys bound to an application or a user, expiration requirement, the secret-bearing `api_keys` output.
- `groups`: IAM groups and their application and user memberships, external membership.
- `policies`: IAM policies, principal selection and rules.
- `users-and-ssh-keys`: invited IAM users and project-scoped SSH keys.
- `deletion-protection`: `terraform_data` guards that block destruction of applications, groups and policies.
